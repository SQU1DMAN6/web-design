# InkDrop 4.0 — Revamp 4
## Task: Drop Sharing, Management & Markdown Notes

**Version:** 4.0
**Task:** Workspace Management + Notes Editor
**Status:** Planned

---

# 1. Purpose

This task implements the first major workspace-level features of InkDrop 4.0.

The frontend shell is now functional. The next step is to make a Drop useful as a workspace by implementing:

1. Drop sharing
2. Drop member management
3. Drop settings and management
4. Markdown Notes
5. Saving and loading Notes
6. Basic Notes file management

The goal is that a user can enter a Drop, manage who has access to it, and create/edit persistent Markdown notes without leaving InkDrop.

This task establishes the first complete "workspace application" inside InkDrop 4.0.

# 3. Drop Management

A Drop is the primary workspace object.

The Drop management interface should be accessible from the existing Drop Information Panel.

The panel should display:

    Drop Name
    Owner
    Visibility
    Members
    Created
    Last Modified
    Storage Usage

The user should have access to relevant management actions depending on their role.

---

# 4. Drop Information

When a Drop is opened, the Drop Information Panel must display current Drop metadata.

Required information:

- Drop name
- Description
- Visibility
- Owner
- Number of members
- Creation date
- Last modified date
- Storage usage

The information must come from the backend rather than being hard-coded into the frontend.

---

# 5. Drop Settings

The Drop Settings interface should allow authorised users to modify Drop configuration.

## Owner-only settings

The owner may:

- Change Drop name
- Change description
- Change visibility
- Manage members
- Delete Drop
- Transfer ownership where supported

## Editor settings

Editors must not be able to modify security-critical Drop settings unless explicitly permitted.

## Viewer settings

Viewers must not be able to modify Drop settings.

---

# 6. Drop Visibility

The Drop must support:

    Private
    Public

## Private

A private Drop is only accessible to:

- Owner
- Explicitly shared members

The Drop must not appear in another user's normal Drop listing unless that user has access.

## Public

A public Drop may be discovered according to the existing public Drop rules.

Public does not automatically grant editing access.

Public access and editing permission are separate concepts.

---

# 7. Sharing Interface

The Share Drop interface should be a dedicated dialog or panel.

Example:

    ┌──────────────────────────────────────────────┐
    │ Share "Project Alpha"                       │
    │                                              │
    │ Add people                                   │
    │ [ Search contacts or users...             ] │
    │                                              │
    │ Permission: [ Viewer ▼ ]                    │
    │                                              │
    │                    [Cancel] [Share]          │
    └──────────────────────────────────────────────┘

The user should be able to search for a contact or user.

The interface must clearly show the selected user's identity before sharing.

---

# 8. Sharing a Drop

Sharing workflow:

    Share
      |
      v
    Search User / Contact
      |
      v
    Select User
      |
      v
    Select Permission
      |
      v
    Confirm
      |
      v
    Backend Permission Check
      |
      v
    Create Membership
      |
      v
    Update Drop
      |
      v
    Refresh Member List

The frontend must not assume that sharing succeeded until the backend confirms it.

---

# 9. Member Permissions

Supported roles:

## Owner

Owner can:

- Manage Drop
- Manage members
- Change permissions
- Edit content
- Delete content
- Upload files
- Create Notes
- Delete Drop

There must be exactly one owner unless ownership transfer is explicitly implemented.

---

## Editor

Editor can:

- View Drop
- Upload files
- Create folders
- Create Notes
- Edit Notes
- Rename objects
- Move objects
- Delete objects

Editor cannot:

- Delete the Drop
- Change Drop ownership
- Modify security-critical settings
- Manage permissions unless explicitly granted

---

## Viewer

Viewer can:

- View the Drop
- Read Notes
- Preview files
- Download permitted files

Viewer cannot:

- Upload
- Create Notes
- Edit Notes
- Rename objects
- Move objects
- Delete objects
- Change Drop settings

---

# 10. Member Management

The Drop management interface must display current members.

Example:

    MEMBERS

    QCHEF
    Owner

    Alice
    Editor                 [⋮]

    Bob
    Viewer                 [⋮]

Each non-owner member should have a management menu.

Possible actions:

    Change permission
    Remove access

The owner must not be removable through ordinary member management.

---

# 11. Changing Permissions

Changing a member's role should use a confirmation interface.

Example:

    Change permission

    Alice

    [ Viewer  ▼ ]

    Current: Editor

                      [Cancel] [Save]

After saving:

1. Backend validates the request
2. Permission is updated
3. Member list refreshes
4. UI reflects the new role

Permission changes must take effect immediately for subsequent API requests.

---

# 12. Removing Members

Removing a member should require confirmation.

Example:

    Remove Alice from this Drop?

    Alice will no longer be able to access
    this Drop.

                [Cancel] [Remove Access]

After confirmation:

- Membership is removed
- User loses Drop access
- Member list updates
- Appropriate activity is generated

---

# 13. Copy Drop Link

The Drop panel must provide:

    Copy Drop Link

When clicked:

1. The canonical Drop URL is copied to the clipboard.
2. The interface displays a temporary confirmation.

Example:

    Link copied

The link must point to the actual Drop rather than a frontend-only placeholder.

---

# 14. Leave Drop

Users who are not owners may have:

    Leave Drop

The owner must not be allowed to leave their own Drop unless ownership transfer exists.

Leaving a Drop removes the user's membership.

A confirmation should be displayed before leaving.

---

# 15. Delete Drop

Deleting a Drop is an owner-only operation.

The UI should make this visually distinct from ordinary actions.

Example:

    Delete Drop

    This will permanently remove the Drop
    and its contents.

    [Cancel] [Delete Drop]

The backend must verify ownership.

The frontend must never rely on hiding the button as the security mechanism.

---

# 16. Drop Management API

Required API functionality should include equivalents of:

    GET    /api/v4/drop/{id}
    PATCH  /api/v4/drop/{id}
    DELETE /api/v4/drop/{id}

    GET    /api/v4/drop/{id}/members
    POST   /api/v4/drop/{id}/members
    PATCH  /api/v4/drop/{id}/members/{user_id}
    DELETE /api/v4/drop/{id}/members/{user_id}

Exact route names may follow the existing API architecture.

All endpoints must perform authentication and permission checks.

---

# 17. Markdown Notes

Markdown Notes are the first native workspace application implemented in InkDrop 4.0.

A Note is a first-class Drop object.

Example:

    Drop
    └── Notes
        ├── Meeting Notes
        ├── TODO
        └── Project Plan

A Note must have a stable object ID.

Its filename or title must not be its identity.

---

# 18. Creating a Note

The Project Manager should provide:

    New Document
        |
        +-- Markdown Note

or an equivalent clearly labelled Notes action.

When selected:

1. Create a new Note object
2. Assign it a unique ID
3. Set the creator
4. Set the creation timestamp
5. Create empty Markdown content
6. Open the Note in Workspace View

Default title:

    Untitled Note

The title must be editable immediately.

---

# 19. Notes Editor Layout

Opening a Markdown Note should replace the Workspace View with the Notes editor.

Recommended layout:

    +------------------------------------------------------+
    | Note Title                     Saved / Saving...     |
    +------------------------------------------------------+
    |                                                      |
    | Markdown Editor                 Preview              |
    |                                                      |
    | # Project Notes                  Project Notes       |
    |                                                      |
    | - Task 1                         • Task 1             |
    | - Task 2                         • Task 2             |
    |                                                      |
    |                                                      |
    +------------------------------------------------------+

The editor should remain inside the existing InkDrop workspace.

The Navigation Panel and Drop Panel should remain available.

The Project Manager should remain available unless the existing UI architecture requires a temporary editor mode.

---

# 20. Markdown Editor

The editing area must accept standard Markdown text.

Example:

    # Project Alpha

    ## Tasks

    - Finish backend
    - Test permissions
    - Write documentation

    ## Status

    The backend migration is complete.

The raw Markdown should remain editable.

The editor should use a monospaced or otherwise clearly code-oriented text presentation.

---

# 21. Markdown Preview

The editor must provide rendered Markdown preview.

Supported rendering should include at minimum:

- Headings
- Paragraphs
- Bold
- Italic
- Links
- Ordered lists
- Unordered lists
- Code blocks
- Inline code
- Block quotes
- Horizontal rules

Example:

    Markdown:

    # Hello

    This is **important**.

    Preview:

    Hello
    =====

    This is important.

The preview must not execute arbitrary HTML or scripts.

Markdown rendering must be sanitised.

---

# 22. Editor Modes

The Notes editor should support:

## Edit

Full-width Markdown editor.

## Preview

Full-width rendered Markdown.

## Split

Editor and preview displayed simultaneously.

Recommended default:

    Split

on desktop-sized displays.

The interface should remember the selected mode during the current session.

---

# 23. Notes Toolbar

The editor should provide a small formatting toolbar.

Required actions:

    Heading
    Bold
    Italic
    Link
    Code
    Quote
    Bullet List
    Numbered List

Toolbar actions should insert or modify Markdown rather than converting the document into a proprietary format.

The underlying document remains Markdown.

---

# 24. Keyboard Shortcuts

The Notes editor should support common shortcuts where practical.

Required:

    Ctrl/Cmd + S
        Save

    Ctrl/Cmd + B
        Bold

    Ctrl/Cmd + I
        Italic

    Ctrl/Cmd + K
        Insert link

The browser's default behaviour should not be broken unnecessarily.

---

# 25. Autosave

Notes must autosave automatically.

Autosave should occur after the user stops editing for a short delay rather than after every individual keystroke.

Example:

    User types
       |
       v
    Wait for inactivity
       |
       v
    Save Note
       |
       v
    Server confirms
       |
       v
    "Saved"

The interface must display the current save state.

Possible states:

    Saved
    Saving...
    Unsaved changes
    Save failed

---

# 26. Manual Save

Ctrl/Cmd + S must trigger an immediate save.

Manual save must:

- Prevent the browser's Save Page dialog
- Send the current content to the backend
- Update the saved state
- Report failure if the request fails

---

# 27. Notes Persistence

A Note must survive:

- Page refresh
- Browser restart
- Closing and reopening the Drop
- Logging out and logging back in

The Note content must be stored persistently.

The frontend must not treat local browser state as the canonical source.

---

# 28. Note Metadata

A Note should store at minimum:

    id
    drop_id
    name
    type
    created
    updated
    created_by
    updated_by

The Markdown content must be stored separately from the object metadata where appropriate.

---

# 29. Note Permissions

Notes must inherit the permissions of their containing Drop unless a more granular object permission system is introduced later.

Therefore:

Owner:

    Read
    Write
    Delete

Editor:

    Read
    Write
    Delete

Viewer:

    Read

A Viewer attempting to modify a Note must receive:

    403 PERMISSION_DENIED

The frontend must also disable editing for Viewers.

---

# 30. Note Renaming

The Note title must be editable.

Renaming should update the object metadata.

The Note's object ID must remain unchanged.

Example:

    Before:

    id: abc123
    name: Untitled Note

    After:

    id: abc123
    name: Meeting Notes

---

# 31. Note Deletion

Notes must support deletion using the existing Trash architecture where available.

Deleting a Note should:

1. Check permission
2. Move the object to Trash
3. Remove it from the normal workspace tree
4. Update the frontend
5. Generate the appropriate activity event

Permanent deletion should remain a separate operation.

---

# 32. Notes File Representation

The underlying representation should remain compatible with Markdown.

A Note may be stored using a `.md` representation internally.

Example:

    Meeting Notes.md

However, the application must treat the Note as an InkDrop object rather than merely exposing a raw filesystem path.

The object ID remains the canonical identity.

---

# 33. Backend Notes Architecture

Notes must use the service architecture.

Required flow:

    NotesController
        |
        v
    NotesService
        |
        +-- PermissionService
        |
        +-- NotesRepository
        |
        v
    Storage

The controller must not directly read or write Markdown files.

---

# 34. Notes API

Required functionality should include equivalents of:

    GET    /api/v4/drop/{drop_id}/notes
    POST   /api/v4/drop/{drop_id}/notes

    GET    /api/v4/drop/{drop_id}/notes/{note_id}

    PATCH  /api/v4/drop/{drop_id}/notes/{note_id}

    DELETE /api/v4/drop/{drop_id}/notes/{note_id}

The API must validate:

- Authentication
- Drop membership
- Permission level
- Note ownership within the Drop
- Content size
- Object existence

---

# 35. Markdown Security

Markdown rendering must be treated as untrusted input.

The renderer must prevent:

- Script execution
- Unsafe HTML
- Dangerous URLs
- JavaScript injection
- DOM injection

A malicious Markdown document must not be able to execute arbitrary code in another user's browser.

---

# 36. Activity Integration

The following actions should generate activity events:

    drop.created
    member.added
    member.removed
    permission.changed
    note.created
    note.updated
    note.deleted

Example:

    QCHEF edited "Meeting Notes"

Activity implementation may use the existing event architecture.

The activity UI itself is not required to be fully implemented in this task.

---

# 37. Error Handling

The frontend must handle:

- Failed sharing
- User not found
- Already shared user
- Invalid permission
- Failed member removal
- Failed Note creation
- Failed Note save
- Note not found
- Permission denied
- Network failure

The user should receive a clear message.

Internal exceptions, database traces, filesystem paths, and other implementation details must not be exposed.

# 42. Non-Goals

Do not implement the following as part of this task:

- Real-time collaborative editing
- Simultaneous multi-user editing
- Document comments
- Full version history interface
- Presentation editor
- Rich text document format
- Advanced search
- External integrations
- Complex object-level permissions

These are future Revamp 4 features.

Markdown Notes should establish the basic architecture for future native workspace applications.

---

# 43. Final Principle

The purpose of this task is to prove two things:

1. A Drop can function as a properly managed collaborative workspace.
2. InkDrop can host native workspace applications inside that Drop.

The result should no longer feel like:

    "A website that lets me browse some files."

It should feel like:

    "This is my workspace, and these are the things I'm working on."

That distinction is the entire point of Revamp 4.
